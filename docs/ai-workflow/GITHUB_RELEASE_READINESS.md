# GitHub Release Readiness

This checklist separates a technically shareable source tree from
owner-controlled publication and legal decisions. It applies to the template
itself and to every project initialized from it.

## Local Technical Gate

- [ ] Python 3.11+ and Bash prerequisites are documented and available.
- [ ] `bash scripts/setup.sh`, `bash scripts/verify.sh`, and
  `bash evals/run-evals.sh` pass from a clean checkout.
- [ ] All Run Guard, Template Doctor, and release-readiness `unittest` suites
  pass with bytecode generation disabled.
- [ ] Template Doctor has no release-content failure beyond the explicitly
  deferred missing-Git-baseline finding (a missing CodeGraph index is an
  optional capability reported as a non-blocking `skip`).
- [ ] The committed `.codex/config.toml` keeps safe defaults
  (`approval_policy = "on-request"`, `sandbox_mode = "workspace-write"`,
  network access off unless explicitly opted in); Template Doctor's
  `config.safe_defaults` rule is part of release validation.
- [ ] The deterministic release build and the independent archive verifier
  pass, including the clean-extraction validation.
- [ ] `bash scripts/integration-test-release.sh` passes from a clean checkout
  (double build byte-identical, clean extraction `--validate`, corrupted
  extracted tree rejected).
- [ ] All project Skills validate; planning plan-doctor reports no failure.
- [ ] `codex --strict-config --version` and `codex doctor --summary` complete
  without project configuration drift.
- [ ] The bounded security scan has no unresolved confirmed finding in
  publication scope.
- [ ] Independent tester and reviewer pass; the final Run Guard gate is ready
  with fresh all-source snapshots.

## Repository Hygiene Gate

- [ ] `.gitignore` excludes planning journals, Python caches, environments,
  secrets, logs, build output, test/eval artifacts, local tooling state, and
  project-local CodeGraph index data, including the exact local Claude
  settings path `.claude/settings.local.json`.
- [ ] `.gitattributes` defines stable line endings and binary treatment.
- [ ] Generated bytecode and cache files have been removed after exact path
  containment checks.
- [ ] Read-only audits find no suspicious sensitive filename/content pattern,
  unexpected large file, reparse point, runtime log, build artifact, author
  absolute path, or active-plan pointer.
- [ ] README, architecture, contributing, security, and changelog documents
  agree with actual commands and contracts and never depend on the Unix
  executable bit.
- [ ] Workflow files are real and configured, never placeholders that imply
  unavailable automation.

## Release Archive Contract

`scripts/build-release.py` builds the archive and manifest from one canonical
release inventory shared with Template Doctor:

- explicit top-level allowlist plus auditable local-state exclusions;
- stable sorting, fixed timestamps, platform-independent storage (no
  compression), and explicit Unix modes;
- relative path, byte size, SHA-256, and intended mode for every entry;
- a deterministic publication digest, so two builds from the same tree are
  byte-identical.

**Clean-source gate.** Inside a Git work tree, the builder resolves HEAD, and
every release file must be tracked at HEAD, present in the work tree, and
byte-identical to its blob at HEAD — otherwise the build is refused and the
offending paths are listed. File content and modes are read from the Git
object database and index, never from the work tree, so uncommitted edits
cannot change published artifact bytes. The release file set is the precise
`.codex` allowlist (`config.toml`, `mcp.example.toml`, and the four named
agent files), never an open directory. Outside a Git work tree the builder
refuses by default; `--allow-unverified` produces an archive explicitly
labeled an unverified-source-tree build.

`scripts/verify-release-archive.py` then checks path containment, duplicate and
case-collision freedom, symlink absence, manifest/digest/size/SHA-256/mode
matching, local-state and privacy-pattern absence, executable-bit policy for
shell scripts, and optional full validation in a clean extraction directory.
The unit-test suite never runs the recursive full validation; the release
integration script performs the double build, byte comparison, clean
extraction validation, and corrupted-tree rejection, and the
release-artifacts workflow executes it on every tag push before generating
`SHA256SUMS` and attaching the Release.

**Source archive contract.** A source delivery must be generated from the
committed tree with `git archive --format=zip --output=template-advanced-source.zip HEAD`.
The source archive contents are derived exclusively from Git `HEAD` and exclude
the `.git/` directory, untracked `.claude/settings.local.json`, `dist/`,
caches, and temporary files. Its ZIP byte representation may vary across Git,
zlib, or operating-system implementations. Cross-platform byte determinism is
guaranteed for the custom release artifacts produced by
`scripts/build-release.py`, not for the convenience Git source archive.

Do not distribute a ZIP created by compressing the working directory: it may
contain `.git/`, ignored files, untracked files, and local tool state. Use
`git archive HEAD` for source delivery or `scripts/build-release.py` for
release artifacts. This is distinct from the formal release archive generated
by `scripts/build-release.py`.

## Owner Decisions

The template itself has completed these decisions:

- [x] Apache License 2.0 selected (`LICENSE`, `NOTICE`).
- [x] Git baseline established with `main` as the default branch.
- [x] GitHub Actions CI, release-artifacts, and security workflows enabled.
- [x] Public GitHub repository created and `v1.0.0` release published.

A project copied from the template must still decide, per copy:

- [ ] Whether to keep the Apache License 2.0 terms and update attribution in
  `NOTICE` (required if the template's copyright notice applies to a fork).
- [ ] Whether to initialize its own Git history and remote.
- [ ] Whether CI and branch protection match the copy's needs.

## Recommended Publication Sequence (for copies)

1. Complete the local technical and hygiene gates, build the release archive,
   verify it, extract it into a clean directory, and re-run the validation
   suite there.
2. Confirm the license and update `NOTICE` attribution for the copy.
3. Initialize Git locally, inspect `git status --short` and the full staged
   inventory, and verify ignored files do not enter the baseline.
4. Commit only after owner approval, then optionally initialize CodeGraph and
   rerun Template Doctor.
5. Create a remote repository with the chosen visibility and security settings;
   do not add secrets or automation by default.
6. Push only after an independent review of the exact Git diff and
   sensitive-data audit.
7. Enable CI, tags, or releases in separate least-privilege changes with their
   own validation and rollback plan.

Until those steps are owner-authorized and completed, the correct status is
**local release candidate**, not published release.

## Security Closeout

Any security scan must target an immutable snapshot of the exact release file
set, never a mutable workspace with planning journals and runtime evidence.
The release archive plus its manifest is the stable scan target: build it,
verify it, scan the extracted bytes, and re-verify the digest before and after
the scan and after independent review. Do not check the Security item in the
local technical gate until the scan covers the full manifest, no unresolved
reportable finding remains, the digest is unchanged, and the final independent
Evidence Ledger is accepted.
